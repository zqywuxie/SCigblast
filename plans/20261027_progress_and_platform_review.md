日期：2026-10-27。基线：本地 main `7b6165c`。状态：2026-10-28 部分实施，记录见文末。

## 1. 范围与结论

本轮只读检查当前已注册五条流程、Web 任务管理/预检/结果/归档/通知及前端模板、JavaScript、CSS。以当前可执行代码为准，不把旧 plans 中已经完成的工作重新列为待开发。工作区原有 AGENT.md、web/README.md 改动及无关未跟踪文件保持不变。

已复核下面的代码路径，并在内存中检查 Pig/Base 日志与当前正则的匹配结果。本轮没有访问线上服务、运行实际分析、浏览器截图验收或性能基准；风险触发条件与改进收益需按后文验收。没有证据支持将所有潜在风险称为线上已发生故障，也不能保证已穷尽平台问题。

推荐先修正进度口径，再增加链内观测与 ETA；随后处理参考库可用性、资源总预算和耗时文件操作。沿用目前克制的蓝灰配色、夜间模式和原生前端架构，重点提升状态理解与操作反馈。

必须保留：

- 全用户共用最多 2 个 pipeline 运行名额；每个 pipeline 最多 4 个 IgBLAST 链任务，资源不足时可以少于上限。
- 分析参数、阶段先后、筛选条件、记录计数、最终 TSV/CSV 内容、列、顺序与命名；Pig/Base 仍在每条链比对后立即筛选发布。
- 原有 flock、进程身份核验、停止/续跑、attempt 隔离、权限与路径边界；Treemap 与主分析的资源互斥关系。
- 不为显示进度拆分原 FASTA、更换 IgBLAST 参数或重排结果。不自动修改历史结果和数据库。
- 验证放在独立临时目录，不重新加入用户已要求移除的项目测试代码；保留正式任务日志。

## 3. IgBLAST 进度设计

### 3.1 用户看到的内容

任务详情首屏保留简洁任务标题、状态、操作区；把当前阶段观测放在运行概览靠前位置。示意数值仅用于布局说明，不是真实测量：

```text
IgBLAST 比对       运行中 4 / 上限 4       已完成 12 / 28 项
阶段已用 00:42:15   预计剩余约 20–35 分钟   5 秒前更新

样本           链     当前操作     已输出查询记录      已用时
A-K266-B       TRA    比对中       62 万 / 100 万      08:10
H-K93-B        IGH    链筛选       比对已结束           12:35
N1-K270-med-B  IGH    比对中       等待输出             00:35

展开全部任务（完成 12 · 运行 4 · 等待 12）
```

- 默认只列当前最多 4 个活动链任务；全清单可按样本/链/状态筛选、分页。IR/10X 的已有批次在样本链下汇总，按需展开批次，不能把批次数当样本数。
- 状态区分：准备输入、等待内部名额/资源、比对、筛选、发布、已完成、复用缓存、失败、停止。未建立输入总数时显示未知，不能当零。
- 总流程显示“已完成 4 / 5 阶段”；IgBLAST 另有自己的完成任务数及序列观测。同一 FASTA 跑多条链时，汇总工作量是“序列×链比对次数”，不能标成去重序列数。禁止把阶段等分百分比作为时间比例。
- 同时显示阶段耗时和本次执行耗时，沿用原有本次运行口径；资源等待时间另标，不混入吞吐计算。
- 进度数据过旧显示“进度更新延迟”，不凭输出暂时不增长判失败，也不自动杀进程。
- 维持现有轮询节奏和局部 DOM 更新，不切走用户当前 Tab，不重建未变化的筛选、按钮或展开区。

### 3.2 先统一事件与任务身份

建议新增 `pipeline_progress.py`，以及 Web 侧独立 `web/job_progress.py`，避免继续把多个分支日志正则堆入 app.py。先接 Base/Pig，再接 reMapping 和 IR/10X 的既有批次。

每次 stage invocation 创建独立 generation，绑定 job/attempt/dataset/stage；CLI 也生成自己的 invocation ID。task_id 使用样本、pair、chain、实际输入身份及已有 batch 身份的稳定摘要，不能仅依赖可重名的样本显示名称。重试不能读到上次遗留 raw 或进度。

建议观测字段：

```text
schema_version, invocation_id, attempt_no, stage, task_id, revision,
sample_id, pair_id, chain, batch_id, phase,
input_sequences, observed_queries, observation_kind,
started_at, updated_at, alignment_elapsed_seconds,
filter_elapsed_seconds, terminal_state, reused, reason_code
```

- 生命周期事件由已有调度器/worker 报告；完成计数仅在对应成功发布/DONE 后增加。失败、缓存复用分开计数；全部任务进入终态不代表全部成功。
- 状态文件置于任务私有 `.pipeline_state/<dataset>/progress/<invocation>/`，不放进用户主要结果清单；历史任务无新文件时保留旧日志回退，但修正 G1/G2，无法确认时显示未知。
- 一份 stage 元信息和按 task 更新的小记录，避免每个 worker 重写全量任务 JSON。进程内统一写入器串行合并变更，原子替换，常态每 2–5 秒发布一次、终态立即发布。
- Web 后台监控一次读取变化事件并维护当前 attempt 的有界索引；事件按游标增量消费、定期压缩为快照。不能在每个列表/详情请求重新遍历所有任务文件或重扫 raw。
- 通过 execution_json 绑定当前 invocation；每条记录使用递增 revision，拒绝旧 generation 和迟到版本。API 总览仅给汇总及最多 4 个活动任务；完整清单走分页接口，仍核验任务 owner。返回显示字段，隐藏 raw 路径、命令参数及内部身份令牌。
- DONE、原子发布结果、现有完成标记仍是分析成功的依据；进度损坏只降级显示。观测异常不得吞掉 IgBLAST 原有失败或伪造成功。
- 更新 Docker COPY、白名单和 check_bundle。将进度显示开关与新版本协议独立，回退 UI/观测不会影响分析结果。

### 3.3 单条链运行时的真实进度

推荐在原有任务监督层旁路增量读取 IgBLAST **未筛选 AIRR**，保留原命令及输入。不要用最终保留行数、mapped/productive 数、文件字节比例或运行时间比例代替已处理查询数。

这是需验证后启用的观测能力：现有代码注释有 outfmt 19 一查询一行的假设，但本轮未验证所部署版本对无命中、异常查询、缓冲输出等情况的表现。实施先检查真实工具行为：

1. 在代表性输入中核验完整输出记录数与有效 FASTA 查询数的关系，覆盖无命中、重复 sequence_id、长序列、空输入、各物种/链和实际参数；不能通过唯一 sequence_id 去重计数。
2. 验证运行中有多少延迟后落盘。只有已完整解析且字段结构有效的未筛选记录才计数，忽略表头，保留未结束的尾部记录；不能简单对任意 TSV 字节块数换行。
3. 对新启动任务先建立 raw 文件的新 generation；不能在工具尚未创建/截断文件前读取上次崩溃残留。只允许处理当前已核验、无旧进程占用的 scratch 文件。
4. 每个读取周期限制字节、行数、时间与尾部缓冲大小，保存 offset；同一时刻最多跟踪现有 4 个活动比对，避免额外全文件扫描。超长记录降级观测而不改变分析；读端追赶积压时标记 catching_up，不用追赶速度训练 ETA。文件替换/截断/消失必须重核身份，不能累加旧数据。
5. 记录含义为“已观察到写出的查询记录”，属于滞后的处理观测。计数关系未通过验证时只展示记录数与耗时，不计算百分比；缓冲很久时明确“等待输出”。
6. 已验证时才显示 `observed_queries / input_sequences` 的序列比例。进程成功退出并不等于整个链任务完成：筛选与发布独立显示，成功终态仍等 DONE。观测超过分母时标为不可用并诊断，不能截成 100% 掩盖口径错误。
7. Pig/Base 过滤后立即删除 raw；监督器不得延迟清理以追赶进度。最终使用已有过滤返回的 raw_rows 等权威计数对齐，不能为补齐最后几条而无限读取。

筛选过程可在现有逐行循环中增加节流计数回调，不新增第二次读取，也不改筛选函数的结果字段与顺序。正式开启前比较观测开/关的结果一致性和资源开销。

若实际版本持续不刷新 raw，第一批仍交付任务状态/耗时/历史 ETA；不能为得到平滑动画默认改成分块比对。精确逐序列进度不可获得时，应明确告知能力边界。

### 3.4 ETA 估计

- ETA 默认仅针对 **当前 IgBLAST 阶段**。IR/10X/reMapping 尚有后续阶段时，不称为“整个任务预计完成时间”；Treemap 独立排队/计时，不混入主任务 ETA。
- 冷启动、观测点不足、速度不稳定时显示“估算中”。有效速率窗口应包含短暂停顿；长时间无新观测时撤回或降低估计可信度，而非停留在旧倒计时。
- 以相同 pipeline/物种/链、数据库版本、IgBLAST 版本、线程配置的历史成功任务作先验；当前阶段有足够观测后优先使用滚动速率。缓存复用、失败、中断不作为普通完整运行测速样本。
- 单任务剩余基于输入规模、可信速率及筛选耗时估计；并发阶段按当前 worker 的剩余负载和实际待执行顺序模拟完成时间。不能把每个任务剩余时长相加，也不能简单取一个平均数乘样本数。
- 两条 pipeline 同时占用服务器、实际 worker 数变化时重新估计；读不到分母、缓存未核验、不同链没有可比样本时允许返回 null。
- UI 显示粗粒度区间和“预计”，区间依据历史/观测离散度；数据不足只给低可信估计或未知，不编造统计置信区间和秒级保证。
- 保留最小历史性能摘要及有界保留策略；不存序列内容，不把其他用户样本名称或任务身份暴露出来。

B2 具体设计：第一版采用两个固定槽位的保守资源分配，CPU 配额/亲和性和 cgroup/主机内存取实际约束，平台总预算先留服务余量后分配各槽位；两槽额度之和不得超过总预算。同一规则覆盖 CLI 与 Web，配置覆盖顺序明确，阶段 guard 与 worker 必须使用同一个 effective_workers，不能一处按配置上限、一处按实际并发计算。单 worker 超额度时等待/明确报不可满足，不能用 `max(1, ...)` 强行启动。内存额度仍是估计而非硬隔离，保留 watchdog。动态借用空闲槽位额度作为后续可选项，不在首批引入复杂抢占逻辑。

B3 必须将“删除中”作为全生命周期状态：同事务核对归属、无活跃进程/派生任务并认领，其他 rematch/resume/archive/treemap 入口拒绝变更。锁外执行删除，失败可恢复；尚未完成前不能允许残存 DB 记录重新启动分析。用户现有确认与路径边界不变。这里是设计计划，不在审阅中执行任何删除。
