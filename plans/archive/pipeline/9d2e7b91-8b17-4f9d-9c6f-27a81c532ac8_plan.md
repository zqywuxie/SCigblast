## 3. 为什么不直接复用 `AIRR_filter_file`

Stage 8 不直接把 `AIRR_filter_file()` 作为输入转换器。该函数会在 UMI provenance 回连之前按：

```text
sample_id（若有） + sequence_id + sequence + locus
```

折叠，并把行数命名为 `umi_counts`。这会过早丢失行级注释信息，也无法证明计数是 distinct UMI。

推荐做法：

- 在 `preprocessing.py` 增加公共过滤 API，例如 `filter_airr_frame()` 和分块/两遍扫描 helper；
- 保持当前过滤语义：`productive`、`v_score > 150`、`v_identity > 85`、V 或 J 有效，TCR 占比大于 90% 时再要求 `v_identity >= 99.7`；
- 旧 `AIRR_filter*` 调用该公共过滤实现后继续执行原有 exact-sequence collapse；
- Stage 8 调用同一公共过滤实现，但不执行旧 collapse，而是在 provenance 回连后做链聚类。

注意：输入是 sample-local `TCR.tsv` 时，TCR 比例通常是 100%，所以默认会触发 `99.7`。该阈值及下述链阈值均为项目配置，不宣称是 10x 官方阈值。

## 4. 输入契约与 provenance 恢复

### 4.1 Stage 7 AIRR 输入

每个 `TCR.tsv` 至少需要：

```text
sequence_id, sequence, locus, productive,
v_score, v_identity, v_call, j_call, cdr3,
sequence_alignment
```

当前 `sequence_id` 解释为 `barcode`；`sample_id` 从 `TCR.tsv` 相对路径取得，不从 barcode 猜测。

当前 Stage 7 发布 `TCR.tsv` 前已经要求 `productive` 且 `v_call` 有效，并删除临时 raw batch IgBLAST 文件。Stage 8 不改变这一历史行为，也不能审计或恢复已被 Stage 7 排除的 nonproductive/无 V 记录；它的过滤统计必须明确以“Stage 7 已发布记录”为输入总体。

### 4.2 Stage 6 provenance 索引

从 `.representative_state.tsv.gz` 读取每个已选代表分子的当前实际列：

```text
sample, barcode, umi, representative_id,
sequence, total_sequences, count, pct,
is_representative, ambiguity_status
```

Stage 8 内部只做语义重命名：`sample -> sample_id`、`sequence -> raw_sequence`、`total_sequences -> total_reads`、`count -> representative_reads`、`pct -> representative_percent`，不回写 Stage 6 文件。

根据 `.representative_fasta_manifest.json` 的技术前缀契约，把 `raw_sequence` 转换为 IgBLAST 实际 query sequence，构造：

```text
(sample_id, barcode, query_sequence) -> distinct UMI evidence set
```

再以 Stage 7 的：

```text
(sample_id, sequence_id-as-barcode, sequence)
```

做精确回连。相同 query sequence 来自多个 UMI 时，不需要强行给重复 AIRR 行逐一编号；聚类支持度直接使用 provenance 中 UMI 集合的并集，避免行顺序造成伪差异。

Stage 8 在自身输出目录生成派生审计表 `provenance_join.tsv.gz`，但不修改 Stage 6/7 文件。

### 4.3 provenance 严格与旧数据模式

- 默认 `REQUIRE_EXPLICIT_PROVENANCE=1`：缺失 state、manifest 不兼容、任一 AIRR query 无法唯一匹配时，该 sample 失败，Stage 8 不发布 `_SUCCESS`。
- 可显式设置 `ALLOW_LEGACY_ROW_SUPPORT=1` 处理旧数据：支持度写入 `legacy_row_count`，`support_mode=LEGACY_ROW_COUNT`，`distinct_umi_count` 留空，所有严格链状态禁用。
- UMI 冲突只能在同一 `(sample_id, barcode, source_library/locus, umi)` 范围内判断：若它对应多个互斥 query sequence，则保留记录并标记 `UMI_PROVENANCE_CONFLICT`，冲突 UMI 不计入 `strict_umi_count`。不同 locus（例如 TRA 与 TRB）恰好出现相同 10 bp UMI 是允许的，不能据此判冲突，也不要求配对链共享 UMI。

## 5. AIRR 过滤与链候选资格

先完整复用当前 AIRR 过滤语义。通过过滤后再增加链聚类所需的资格检查：

```text
locus in {TRA, TRB, TRG, TRD}
AND v_call 有效
AND j_call 有效
AND cdr3_nt 非空且只含允许的核苷酸/IUPAC字符
```

原过滤保留“V OR J”；链聚类资格使用“V AND J + CDR3”。未通过资格检查的行写入 `rejected_records.tsv.gz`，带可组合的 `rejection_reason`，不得静默丢弃。

规范化规则固定并写入 schema/config hash：

- `sample_id/barcode/locus/v_call/j_call`：去首尾空格；locus/call 大写；多值 call 拆分、排序、去重后重组；不主动去除 allele。
- `cdr3_nt`：使用 AIRR `cdr3`，大写并移除空白；不使用 `cdr3_aa` 代替。
- `normalized_sequence`：`sequence_alignment` 大写并移除空白、`.`、`-`；缺失时可回退到 `sequence`，同时标记 `NORMALIZED_SEQUENCE_FALLBACK`。
- `c_call`、`d_call`、normalized sequence 均不进入链身份键。

## 6. 聚类规则

生物学 cluster 唯一键固定为：

```text
sample_id + barcode + locus + v_call + j_call + cdr3_nt
```

规则：

- 相同 V/J/CDR3 nt、多个 normalized sequence：合并为同一 cluster；记录变体数、各变体支持度和冲突标记。
- 不同 CDR3 nt：始终保留为不同 cluster，即使 V/J 相同或 CDR3 aa 相同。
- 不跨 sample、barcode 或 locus 合并。
- `c_call` 冲突不拆 cluster，记录 `c_call_set` 和 `C_CALL_CONFLICT`。

cluster ID 使用规范化 key 的稳定 SHA-256 前缀，确保输入顺序变化时 ID 不变。

## 7. normalized sequence 代表值的确定性选择

不合成新 consensus；从已观测 normalized-sequence 变体中选一条，保证可追溯。变体排序依次为：

1. `strict_umi_count` 降序；
2. `distinct_umi_count` 降序；
3. Stage 6 `representative_reads` 去重后总和降序；
4. 支持该变体的 AIRR 行数降序；
5. 对齐覆盖长度降序；
6. `v_score` 降序；
7. `v_identity` 降序；
8. normalized sequence 字典序升序；
9. 原始行号升序。

对应 AIRR 代表行再按同一质量顺序选定。输出同时保留：

```text
representative_normalized_sequence
representative_variant_umi_count
normalized_sequence_nunique
normalized_sequence_conflict
all_normalized_sequence_support
```

## 8. 同一 barcode/locus 下的自动排名状态机

支持度优先使用 `strict_umi_count`，其次仅用于展示的是 `distinct_umi_count`、representative read support 和 row count。所有阈值都写在 `08.chain_resolution_config.env`，输出记录其值与 config hash。

建议初始默认值（非 10x 官方标准，必须用本项目阳性对照和样本分布校准）：

```text
MIN_UMI=3
MIN_ALT_FRACTION=0.10
CO_DOMINANT_RATIO=2.0
DOMINANT_RATIO=3.0
```

对于一个 `(sample_id, barcode, locus)`：

1. 所有 cluster 按第 7 节证据顺序确定性排序，全部写入 `chain_candidates`。
2. `support < MIN_UMI` 或 `support / locus_total_support < MIN_ALT_FRACTION`：标记 `LOW_SUPPORT`，保留但不进入 active-chain 集。
3. 没有 active cluster：`LOW_CONFIDENCE_LOCUS`。
4. 只有一个 active cluster：它为 `PRIMARY`；若不存在任何其他 cluster，细化为 `UNIQUE_CHAIN`。
5. 至少两个 active cluster，令 `ratio=top1/top2`：
   - `ratio <= CO_DOMINANT_RATIO`：top1/top2 为 `CO_DOMINANT`，barcode 标记 `MULTI_<LOCUS>`；例如 43/41。
   - `ratio >= DOMINANT_RATIO`：top1 为 `PRIMARY`，top2 及其余 active 为 `SUBSTANTIAL_ALTERNATIVE`；仍不删除 alternative，该 barcode/locus 保持多候选状态。
   - 两阈值之间：相关 active cluster 标记 `UNRESOLVED_TOP`。

因此：

```text
43/41 -> 两条 CO_DOMINANT，保留，barcode 标记 MULTI_CHAIN
43/10 -> PRIMARY + SUBSTANTIAL_ALTERNATIVE，均保留，barcode 标记 AMBIGUOUS_CHAIN
43/2  -> PRIMARY + LOW_SUPPORT，均保留
2/1   -> LOW_CONFIDENCE_LOCUS，均保留并标记低置信度
```

阈值只决定角色与严格集资格，从不删除候选链。

## 9. 每个 barcode/locus 的链状态

本阶段只做每个 barcode 下每种 locus 的链候选解析，不生成 TRA/TRB 或 TRG/TRD 配对文件。

输出状态：

```text
UNIQUE_CHAIN
PRIMARY
LOW_SUPPORT
CO_DOMINANT
SUBSTANTIAL_ALTERNATIVE
UNRESOLVED_TOP
LOW_CONFIDENCE_LOCUS
MULTI_CHAIN
INVALID_PROVENANCE
```

例如：

```text
一个 barcode + 一个 TRA cluster -> UNIQUE_CHAIN
一个 barcode + 两个 TRB 且支持度 43/41 -> MULTI_CHAIN / CO_DOMINANT
一个 barcode + 两个 TRB 且支持度 43/2 -> PRIMARY + LOW_SUPPORT
```

TRA、TRB、TRG、TRD 之间只在 QC 中分别统计数量，不在 Stage 8 内建立受体配对关系。若未来需要配对，应以本阶段输出的 active/primary 链为输入另行设计，不回写本阶段结果。

## 10. 输出契约

根目录：`<OUTPUT_ROOT>/08.chain_resolution/`

1. `filtered_records/<sample>/<locus>.csv`
   - 在用户现有字段前增加 `sample_id, barcode`；保留其字段列表；增加 `support_mode, distinct_umi_count, legacy_row_count, provenance_status`。
   - 这里的 `umi_counts` 仅在 explicit provenance 下表示 exact-query 的 distinct UMI 数；legacy 模式留空，避免把行数冒充 UMI。
2. `chain_candidates.tsv.gz`
   - 一行一个 V/J/CDR3 cluster；含 cluster key/ID、代表 AIRR 字段、normalized-sequence QC、UMI/read/row 支持、rank、role、flags、证据 UMI/representative IDs。
3. `barcode_chain_qc.tsv.gz`
   - 一行一个 `(sample_id, barcode)`；各 locus 的候选数、链状态、multi-chain、legacy 和 provenance flags；不包含配对 ID。
4. `rejected_records.tsv.gz`
5. `provenance_join.tsv.gz`
6. `run_summary.json`、`schema.json`、`_SUCCESS`

每张主表包含：

```text
schema_version, run_id, filter_profile,
threshold_config_hash, stage7_input_hash, stage6_provenance_hash
```

Stage 8 先写进同输出根下的 `.tmp.<pid>`，完成 schema、计数和不变量检查后再逐文件 `os.replace`；`_SUCCESS` 最后写。失败时不得留下可被 runner 误认为成功的输出。

## 12. 失败模式与处理

| 失败/异常 | 行为 |
|---|---|
| AIRR 必需列缺失、TSV 损坏 | sample 失败；Stage 8 不发布 `_SUCCESS` |
| Stage 6 state/manifest 缺失 | 默认失败；显式 legacy 模式才继续，并标记严格链状态不可用 |
| sample/path 与 provenance sample 不一致 | 失败，禁止跨 sample 猜测 |
| AIRR query 无 provenance 匹配 | 默认失败；legacy 模式标记 `UNMATCHED_PROVENANCE` |
| 一个 UMI 在同一 locus 对应多个 query/互斥 cluster | 保留并标记；冲突 UMI 不计入 strict_umi_count，相关 barcode/locus 不进入高置信度链状态 |
| V/J/CDR3 缺失 | 写 rejected 表，不参与 cluster |
| 同 cluster 多 normalized sequence | 合并，确定性选代表并标记冲突 |
| c_call 不一致 | 不拆 cluster；记录集合与冲突 flag |
| 无 TCR 或全部被过滤 | 输出带完整 header 的空表和 summary；若输入本身有效则成功 |
| 输出中途失败 | 无 `_SUCCESS`；重跑从 Stage 8 临时输出重新生成 |

## 13. 测试与端到端验证

### 单元测试

1. 过滤边界：`v_score` 150/151、`v_identity` 85/85.1/99.7、productive T/TRUE、V OR J。
2. TCR 占比 0.9 与大于 0.9 的两遍判断，确认旧 API 和新 filter-only API 结果一致。
3. provenance：同 sequence 多 UMI、同 barcode 跨 sample、missing state、manifest 不兼容、同 locus 内 UMI 多序列冲突，以及跨 locus 相同 UMI 不得误报冲突。
4. cluster：
   - 同 V/J/CDR3、多 normalized sequence -> 1 cluster；
   - 同 V/J、不同 CDR3 nt -> 多 cluster；
   - 同 CDR3 aa、不同 CDR3 nt -> 多 cluster；
   - c_call 冲突不拆 cluster；
   - 输入随机打乱后 cluster ID、代表序列、rank 完全一致。
5. 状态机：43/41、43/10、43/2、2/1，并验证所有候选仍在 `chain_candidates`。
6. 链状态：单链、43/41、43/10、43/2、低支持度、多链、混合 locus 和 orphan。

### 集成测试

1. 用最小 Stage 6 state + manifest + sample-local Stage 7 TCR fixture 运行 `08.resolve_tcr_chains.py`。
2. 校验链候选、过滤记录、barcode chain QC 等输出的 schema、计数守恒、链状态分流和 QC flags。
3. 运行前后计算 `07.igblastn_out` 全部文件 SHA-256，必须逐文件一致。
4. 连续运行两次，第二次命中 marker；删除 `_SUCCESS` 后只重跑 Stage 8。
5. 修改 Stage 8 阈值或代码 hash，只失效 Stage 8；Stage 1–7 marker 保持可复用。
6. 使用同 barcode、不同 sample fixture，确认绝不跨 sample 合并。
7. legacy fixture 缺失 provenance：默认失败；启用兼容开关后候选表可生成、严格链状态必须禁用。

### 大文件/资源测试

## 15. 完成标准

- Stage 7 所有输入文件运行前后字节级不变。
- distinct UMI 支持可追溯到 Stage 6；无法追溯时绝不冒充 UMI。
- 聚类严格使用 `sample_id+barcode+locus+V+J+CDR3_nt`。

- 同一输入重复运行的 cluster ID、排序、代表序列和输出内容稳定。
- 链候选和 barcode chain QC 完全分离；本阶段不生成任何配对输出。
